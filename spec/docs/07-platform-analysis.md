# 07. Анализ: как реализована запись экрана на разных платформах

Цель: понять ограничения и взять лучшее. Детали API перепроверяй по официальной документации.

## Android (целевая платформа)
- Механизм: `MediaProjection` даёт `VirtualDisplay`, который рисует копию экрана на `Surface` (энкодер или `ImageReader`).
- Согласие: системный диалог при каждой записи. С Android 14 токен одноразовый и привязан к сессии. Android 15 добавил запись отдельного приложения и уведомление о записи экрана для других приложений.
- Foreground service типа `mediaProjection` обязателен.
- Звук: микрофон через `MIC`; звук системы через `AudioPlaybackCapture` (Android 10+), приложения могут запретить захват.
- Аппаратное кодирование через `MediaCodec` (`H.264`, `HEVC`, на новых устройствах `AV1`).
- Точки входа, которые есть только на Android: плитка шторки (`TileService`), виджет, оверлей-плашка, `adb shell screenrecord`.
- Фрагментация: у производителей свои встроенные рекордеры и свои ограничения фоновой работы (энергосбережение может убить сервис).

## iOS (для справки)
- `ReplayKit`: `RPScreenRecorder` для записи своего приложения; `Broadcast Upload Extension` для всей системы.
- Системная запись через Пункт управления, у приложений нет своей плитки.
- Лимит памяти расширения (около 50 МБ) заставляет делать обработку очень экономно.
- Вывод: не целевая платформа; Flutter-слой можно переиспользовать, нативное ядро писать заново.

## Windows / macOS / Linux
- Windows: Game Bar, `Windows.Graphics.Capture`, Desktop Duplication API.
- macOS: `ScreenCaptureKit` (современный), старый `AVCaptureScreenInput`.
- Linux: Wayland через PipeWire и xdg-desktop-portal (согласие обязательно), X11 через `x11grab`.
- Вывод: не нужны.

## Web
- `getDisplayMedia` + `MediaRecorder`; пользователь выбирает экран, вкладку или окно.
- Нет контроля над битрейтом на уровне энкодера в полной мере, формат WebM/MP4 зависит от браузера.
- Вывод: не подходит для цели «качество и контроль».

## Инструменты, которые полезно изучить как референс
- `scrcpy` (зеркалирование/запись по adb): образец низкой задержки.
- Встроенные рекордеры One UI, MIUI/HyperOS, Pixel: сравнить набор настроек и расположение кнопок (для UX-ориентира, не для копирования).
- AOSP `ScreenRecordingService` (SystemUI): эталон поведения плитки, уведомления и таймера отсчёта.
- Проекты с открытым исходным кодом для записи экрана: посмотреть, как организован MediaCodec-пайплайн со звуком системы.

## Сравнение UX-паттернов
| Паттерн | Встроенные | Магазинные | DotRec |
|---|---|---|---|
| Старт | Плитка, диалог с опциями | Плавающая кнопка, виджет | Плитка, виджет, приложение, без плавающей кнопки по умолчанию |
| Настройки | Мало, спрятаны | Очень много | Пресеты + 6 ключевых |
| Реклама | Нет | Часто | Нет |
| Индикатор записи | Красный чип в статус-баре | Оверлей | Уведомление + опциональная плашка |
| Остановка | Статус-бар, шторка | Оверлей | Уведомление, плитка, виджет, плашка |

## Выводы для DotRec
1. Единственная реальная фрагментация находится в Kotlin, поэтому всю сложность прячем там.
2. Плитка и виджет самые быстрые входы; приложение нужно в основном для настройки.
3. Оверлей-плашка даёт удобство, но требует опасного разрешения, поэтому выключена по умолчанию.
4. Звук системы реализуем во второй итерации, чтобы не рисковать стабильностью v1.
